## 二、我们的实测

**方法**：把新件归位到 `engine/upstream-20261008/`（配 `engine/` 的官方 DLL），用 `serve_tee.py` 起**可见窗口**，端口 **8096**；参数 `k8v4 / kv-capacity 17920 / max-context 262144 / host-kv 16384 / spec dflash2 K=7`；KVMem 五环境变量照旧注入。

### 2.1 起服 / 判活 ✅
- 起服正常，`listening on http://127.0.0.1:8096`；`weights ready 8.16 GiB`。
- `capacity | KV 17,920 tokens, k8v4, explicit | pages 280/4,096 | runtime 1.98 GiB | **free 5.40 GiB**` ——**显存余量远大于旧版**（旧版同档约 0.8 GiB 级）。
- `/v1/models` **200**；真发请求 **200**（"1+1 等于 2。"）。

### 2.2 S3 · per-request `thinking_budget` ✅（重大）
- `thinking_budget=128` → **HTTP 报错**：`"thinking_budget must be at least 1024 when set"`（`invalid_request_error`）⇒ **确认 OpenAI 路由解析该字段**。
- `thinking_budget=1024` → 正常返回；完成记录 **`thinking 78/1,024`** ⇒ **逐请求思考预算生效**。
- ⚠️ **这与我们既有结论冲突**：我们此前记录"OpenAI chat 端点不解析请求体 `thinking_budget`，只能靠服务端 `--default-thinking-budget`"——**该结论对 20261008 版已不成立**。

### 2.3 超池行为（对比我们记录的"挂起"）✅
- 发 **prompt 18,051 tokens**（> 池 17,920）：**正常返回 200**（`finish=output limit`），**引擎存活**（无挂起、无杀进程、无 429）。
- 新日志：**`[ninfer] mask hidden: which=text site=mapped/commit span=284 resident=271 hidden=13 first_hidden=11 last_hidden=23 mid_hidden=0`**
  ⇒ 超池时**隐藏/淘汰 13 块** —— **正是我们挂账的"淘汰式检索"（此前"题面超池但 kept 全保留、未观察淘汰"），本版已实现**。
- **深挖（28,051 tokens，更严重超池）**：**仍 200、无 429、引擎存活**；`mask hidden … span=440 resident=272 **hidden=168** first_hidden=131 last_hidden=298 **mid_hidden=145** mid_lo=154 mid_hi=308` ⇒ 更严重超池时**淘汰更多、且含中段**。
  ⚠️ **B01 的"429 可见拒绝"在这些场景未触发**（上游自陈"未验"）；实际缓解路径 = **淘汰（mask hidden）**，引擎**不挂起 / 不崩**。

### 2.4 其他观察
- 新日志机制：`[ring] budgets: skeleton=4, evidence=128, recent=0, free=148 (pool 280)`（**预算分解**，本版新增）；`harvest_layers=16/16`；`kvmem_index blocks=4096`。
- 完成记录 `finish` 新版用 **`output limit`**（旧版 `length`）。
- 强复读请求（要求重复输出 300 次）：`output 2,048` 用尽、**返回正文为空（len=0）** ⇒ "输出限制 → 空正文"**疑似仍存在**（待查：属思考占满还是复读）。
- **日志刷屏加剧**：`[ring] budgets` 与 `mask hidden` 高频重复（密度高于旧版 `KEPT`）。

### 2.5 补验（第二轮，已做）

**S6 复读指标 ✅**（需 `--request-log-jsonl`；字段在 jsonl 的 `result` 内）：`schema_version=28`，`repeat_channel / repeat_tokens / repeat_uniq8 / repeat_dup8 / repeat_max8` 均在。样例（复读请求）：
`completion_tokens=2048, finish_reason=output_limit, repeat_channel="reasoning", repeat_tokens=847, repeat_uniq8=0.9976, repeat_dup8=0.0024, repeat_max8=2, model_thinking_tokens=0, thinking_budget=null`
  ⇒ **关键**：该请求**正文为空（len=0）**，真相是**输出全花在 `repeat_channel="reasoning"`（推理通道）** —— 即 **"思考占满输出 → 空正文"在新版仍会**（未设 budget 时）；**S3（per-request thinking_budget）正是对症解法**（前测 budget=1024 时 `thinking 78/1024` + 正文正常）。

**B25 负控 ✅**：设 `NINFER_TERNARY_KVMEM=0` ⇒ 引擎打印 **`content scorer was EXPLICITLY DISABLED … falls back to the lexical IDF ranking`**（负控**真生效**）。上游并给效用对比：**lexical 4/6 vs content 6/6**（同 restore budget；pool 4000 时 2/6 vs 6/6）。
  - 附带情报：显式开启形状 = `NINFER_TERNARY_KVMEM=1` + `NINFER_TERNARY_KVMEM_SCORE=1` + **`NINFER_TERNARY_KVMEM_SCORE_QUERY_TAIL=64`（问题窗口，禁止放宽**：缺失会跳过每个 chunk，放宽会在小池误排）。**我们此前未设该 tail。**

## 三、对本项目的价值

### 高价值（直接对症我们踩过的坑）
1. **S3 per-request `thinking_budget`** — 我们"思考墙空正文"的**服务端单点设置**限制解除，客户端可逐请求控。
2. **B01 容量失败分类 / 不杀进程** — ⚠️ **经 CODE 交叉审核纠正（2026-10-08）**：**B01（池超）≠ A4（池未超下的 prefill 死锁）**，两者路径不同 ⇒ **A4 须在新基线复测，不得视为已被 B01 解决**。（本稿原“B01 对症 A4”为**误**，此处已改。）
3. **`mask hidden` 淘汰式检索** — 补上我们 **G15 挂账**的"未观测到选择性淘汰"。
4. **B30 KV 窗口门统一** — 我们用 KVMem 环 + `NINFER_KV_*`，可能踩过"照提示操作必崩"。
5. **B29 T2 conv 重复平面（真数值 bug）** — **输出正确性**修复。
6. **S6 复读指标** — 我们的"**思维循环**"从肉眼变可量化。
7. **B25 布尔 `=0` 生效** — 我们若用 `NINFER_TERNARY_KVMEM=0` 做负控，此前可能是**空操作**。

### 中价值
- B21 启动守卫 / B02 503 / B03 MTP 守卫 / B06 并发门 / B32 检索预算默认 / 件小一半（省空间，速度不变）。

## 四、影响与风险

1. **Design C 与 S3 的关系：经 CODE 源码级论证 = 协同而非覆盖**（CODE 稿 §2.4/§4.3）：**S3** 把请求体 `thinking_budget` 送进 `preview_semantic.budget`；**Design C** 治的是“**已有 budget、模型仍在思考区自行吐 EOS**”⇒ 两者**合起来才完整覆盖空正文**。⇒ Design C **倾向保留为兜底**（低成本 12 行 / 原位重放）；**但本稿实测的只是“无 budget → 占满”场景，“有 budget 吐 EOS”场景双方尚未实测，建议补一次对照。**
2. **跟进 = 基于新版源码重打补丁**：我们现用的自编件基于 `20261003` 源码 + 我们的 8 处补丁；跟新版要**在新源码上重来**（3 类 MSVC 兼容补丁是否仍需要，需重核）。
3. **工具链要适配**：
   - `serve_tee.py`「精简」需**新增过滤规则**（`[ring] budgets` / `mask hidden`）；
   - 日志解析要认 **schema 28** 与新的 **`output limit`** finish 值。
4. **环境项**：驱动 ≥580；一 exe 一架构（无 PTX 回退）；8 GB 卡加 `--no-cuda-graph`。
5. **B01 上游自陈"未验"**（复现条件其本机无）⇒ 不宜当作已彻底解决。

## 六、迁移决策分析（不是"直接迁移"这么简单）

> 背景：我们这几天的成果是**针对本机环境重编译**得到的（自编引擎 + 运行环境 + 补丁）。上游出了 20261008 新件后，问题变成：**直接迁移会浪费我们的成果吗？还是只替换"引擎"这一个，成果仍在？**

### 6.1 "我们的成果"分三类，各归各位

| # | 成果 | 换成上游新件后 |
|---|---|---|
| ① | **工具 + 文档 + 复现材料**（GUI 启动器 · 日志工具 · 构建脚本 · 产物清单 · 构建史/报告） | ✅ **完全保留、继续有用**——它们与"引擎由谁编译"**解耦**（操作的是"引擎 + 模型"） |
| ② | **我们的补丁**（MSVC 编译兼容 ×7 · 思考区收尾补丁 Design C） | ⚠️ **部分可退役**：MSVC 兼容补丁**只在"我们自己编"时才需要**（上游自带成品件）；Design C **待比对**（见 6.3） |
| ③ | **自编引擎二进制**（`engine/self-built/` 4 exe + 环境） | 🔁 **会被替换的只有这一个**；但**能力/方法没丢**（补丁法 / 构建脚本 / 复现材料都留着） |

⇒ **结论**：**只替换"引擎二进制"这一样**，**成果①（工具/脚本/文档）全部还在、全部有用**——**不算浪费**；真正闲置的只有 **② 里的 MSVC 兼容补丁**（因为上游已替我们编好）。

### 6.2 三条路径

| 路径 | 做法 | 代价 | 收益 |
|---|---|---|---|
| **A · 直接迁移** | 引擎用上游新件（我们的工具照用） | ≈ 0 | 立刻拿到 B01/B29/B30/S3/S6/B25 全部修复 |
| **B · 在我们基础上吸收** | 把上游新源码/改进移植进**我们的自编基线**（重打补丁、重编、重验） | 大 | 保留"能自己改引擎"的能力，成果**升级**而非废弃 |
| **C · 混合（先走这个）** | 先用 A 跑起来（引擎=上游新件）；**保留 B 的素材**（我们的基线/补丁/脚本不删），只在需要"自己改引擎"时再做 B | 低 | 立刻受益 + 保留后路 |

### 6.3 Design C 作为"综合兜底防御"可行吗？（有条件可行）

**两种"兜底"，成本/价值差很远：**

| | ① 低成本兜底（保留现有自编件，切换用） | ② 真兜底（**在 20261008 新基线上重打 Design C**） |
|---|---|---|
| 做法 | 现有 `engine/self-built/`（20261003 源码+补丁）留着，启动器「引擎」下拉切换 | 在新源码上重打 MSVC ×7 + Design C → 重编 → 重验 |
| 成本 | ≈ 0 | 高（每跟一版都要重来） |
| 关键问题 | ⚠️ **旧基线**：缺 20261008 全部修复 ⇒ **等于用更旧的引擎给新引擎兜底**，逻辑倒挂 | 无此问题 |

⇒ **① 严格说不算兜底**；**② 才是有意义的兜底**，但要持续维护两套。

**成立前提（必须先证）**：**Design C 得能治 S3 治不了的场景**，否则兜底=纯冗余。
- 上游 **S3** = "**按请求设 `thinking_budget`**"（**被动**：给手段）；
- 我们 **Design C** = "**模型在思考区 `stop` 时自动强制转正文**"（**主动收尾**）；
- **实测线索**：新版**不设 budget 时仍出现"输出全花在 `reasoning` → 正文空"**（见 2.5）⇒ **新版并不会自动收尾**。
⇒ **Design C 很可能有独立价值**（"自动兜底" vs "手动设预算"），但**必须一次对照实验才算数**。

**兜底的工程要求**：切换机制 ✅ 现成（启动器「引擎」下拉）；**缺两样**——**触发条件**（什么现象判"上游件出问题、该切兜底"）与 **验证**（兜底件自己得起、能出正文）。

### 6.4 建议（分两步，均可逆）

1. **先做一次对照实验**（Design C vs S3）：同一"会触发思考区 `stop`"的 prompt，分别跑【上游新件（不设 budget）】/【上游新件 + per-request budget】/【自编件（Design C）】→ 看**谁能自动出正文**；
2. **再按结果定路径**：
   - Design C **独有** ⇒ 兜底值得养 ⇒ 走 **C + ②**（在新基线上重打补丁；启动器切换 + 定好触发/验证）；
   - Design C **被 S3 覆盖** ⇒ 兜底无意义 ⇒ 走 **A**。
3. **在此之前，任何件都不清**（上游新件、自编件、`engine/` 原对照件全留）。
