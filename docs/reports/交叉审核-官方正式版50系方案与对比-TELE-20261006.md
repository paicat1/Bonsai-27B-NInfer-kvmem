## 2. 对 CODE 对比报告逐节审核

### 2.1 定性（§1）—— 认可
三元 Bonsai 官方成品线、原生 sm_120a、启动器三档、模型独立分发的判断，我实核无误。

### 2.2 差异表（§2）—— 基本属实，一处需补正
- "自建引擎体积 ~226MB（3 exe）" vs 官方 1.34GB 单 exe：属实（官方单架构无 PTX 兜底）。
- "视觉：无（M0 已判三元线不支持）" vs 官方 `--vision`：**需注意**——官方 `start-pq2-dflash.bat` 默认开 `--vision`，而官方模型包里三元 dflash 版是否真含视觉权重、16GB 卡能否驻留，官方并未验证。R5 已列，采纳。

### 2.3 ⚠️ 最核心争议：接受率对比口径错误（必须纠正）

CODE 对比报告 §3 用这张表作核心支撑：

| | 我们 | 官方 | 倍数 |
|---|---|---|---|
| MTP 接受率 | 44.0% / 45.9% | 88.1% | ~2× |
| DFlash2 接受率 | 5.4% / 21.3% | 91.5% | 4~14× |

**问题：两端不是同一语料、不是同一 draft 深度。**

- 官方 88.1% / 91.5% 与 237.9 / 571.9 tok/s 全部来自教程 §0.2 的**"数数字"语料**（1..300 接着数，`temperature=0`，且官方原文自己强调"语料不能换：换散文 decode 掉一半"）。
- 我们的 44.4% / 5.4% 来自 M6 报告的**散文语料**（中文"秋天图书馆"256token / 英文 essay，256 token）。
- 接受率是**强依赖内容**的量（作者 + 我们 M6 §4.5 都反复强调：中文短答 80%、代码 40.8%、文章长 output 会掉到 54.8%）。数数字是"可预测序列"，接受率天然极高；散文接受率天然低。
- **因此"官方 88.1% vs 我们 44.4%"这个 2 倍差距，绝大多数可能是"数数字 vs 散文"的语料效应，而不是"v3 vs v2"的制品效应。** 用这个数支撑 H1（"差距根因在制品"）在方法上不成立——**这是拿两个不同语料的读数做减法**。

MTP/DFlash2 的 draft 深度也不同：官方 MTP=4、DFlash=12（README-pack 明示 dflash 用 12 才是官方口径），我们 M=2、DFlash=7。接受率随 draft 深度上升而下降（我们 M6 实测 K1=54.4%→K2=44.0%），官方 K 更大反而更高，这更加说明两端量度不同域。

> **结论：H1（"接受率差距根因在制品代际"）当前不可证。要用同语料、同 draft 深度、同 KV dtype 才能证。** 这正是 CODE 自己 §10 第 2 问担心的点，实际比 CODE 想的更严重——连语料都对不齐。

### 2.4 建议动作（§5）—— ✅ 方向对，但需按语料对齐重设判据
CODE 建议"与自建线做同口径 A/B 验证接受率是否恢复到 88% 量级"——方向对，但把"恢复到 88%"当目标本身就是语料误区（88% 是数数字语料的期望，换成散文不可能到 88%）。**正确目标应是"同语料下官方接受率是否显著高于自建"**，而非"是否=88%"。

## 3. 对方案 v2.0 的审核（重点：§10 七问逐条回应）

### Q1 H1 可证伪性 —— 🔴 需修正，见 §2.3
CODE 自问"接受率会不会受引擎实现影响"。我的回答：**比引擎更根本的问题是语料口径。** 接受率跨机器可比是对的，但前提是**同语料同 draft 深度**。当前支撑 H1 的两个数就不同源。修法：N3 必须让两条线跑**完全相同的题面**（建议直接用官方数数字题面 + 我们自家中文/英文散文题面各一组），同 draft、同 max_tokens、同 greedy。这样 H1 才是单一变量（制品代际）实验。

### Q2 N3 同口径是否公平 —— 🔴 不够公平，必须统一 draft 数
CODE 方案 N3.2 已要求"同 prompt、同 max_tokens、同 greedy、同 KV dtype、同上下文"——很好，但**漏了"同 draft-tokens"**。官方 M=4/DFlash=12，我们基线 M=3/DFlash=7。必须在两边跑**同一 draft 数**（比如都 M=4、DFlash=7），否则即使语料统一，接受率也会因 draft 深度不同而无法归因。**这条从"Q2 自问"升级为方案硬性要求。**

### Q3 N1 判据是否足够 —— 够，但建议补一条"中文散文烟测"
官方教程的 15 分钟判据（起服 + 两条 KVMem 日志 + 一条数数字测速）我认可，足够作为"能否起服"的验收。但因为是判"可用性"（不是只判"起得来"），建议**加一条自家中文散文短答**（比如 64 token），因为数数字测速只证明引擎跑得动，不证明真实中文输出质量——这个字段我们在 M6 已经踩过（数数字通过不代表长文不空）。

### Q4 R1 缓解是否充分 —— 够，但可补第四条路

### Q5 遗漏的官方能力 —— 补充 3 个值得进 N3/N4

- `--preserve-thinking` / `--max-pending-requests`：暂不急需，记入附录备查。

### Q6 v3 制品获取渠道 —— 我这边不知道
TELE 侧无 `modelpack-pq2-v2-20261002` 的分发地址（`J:\分发\正式版50系` 只有引擎包，ZIP-README §五 指向 `E:\ship-next` 不存在，本机全盘未见 v3 .ninfer）。**P2/P3 硬阻塞成立，只能由用户/UP主提供。** 与 CODE 判定一致。

## 9. K 值问题澄清（答用户质询：DFlash 是否已修 K>7？为何"强制 K=7"？）

**用户问**：这个模型和引擎是不是已经修复了 DFlash K 大于 7 的问题？为什么要强制降级到 K=7？

**答：不存在"K>7 缺陷"，也不应"强制 K=7"。** 分四层：

1. **M6 遇到的障碍不是 K，是 DFlash2 "Full 头"崩溃**：`FATAL … linear_topk: unsupported head profile`（Full 头要求行数 248320，实际 token_domain=248077）。触发条件 = **不加 `--lm-head-draft`**（此时走默认 Full 头）；**与 K（draft-tokens）取值无关**（[EVIDENCE] M6 报告 §4.1，`linear_topk_workspace.h:15` / `frontend.h:16`）。
2. **"修法"是加 `--lm-head-draft`（切 Optimized 头），不是调 K**：M6 §3.3 实测带该参数 **K=7 成功**（英文 104.7 t/s）。
3. **官方口径 K=12**：官方 `start-pq2-dflash.bat` 默认 `--draft-tokens 12`；教程原文"用 dflash 版本模型时必须把 dflash 窗口数设成 12（不是 4）"，实测 12 vs 4 = 600 vs 278 tok/s（约 2.2×）。K 的合法范围 1–15。
4. **官方是否"修了"Full 头崩溃**：官方 Release body 明示"带 dflash2 头的权重用 `--spec dflash2 --lm-head-draft`"⇒ 官方以**"规定必须用 Optimized 头"**处理，**不依赖 Full 头**；官方缺陷台账（`已知问题-初期版本.md`）**未把 Full 头崩溃列为未关闭项**（其 B18 记的是 dflash2 头**质量**在特定模型偏低 22%/47%，属另一问题）。另，旧包 `42CD0735…` 有一条 B16 残留崩溃（`0xC0000005`）待用新清编件复测。

**"K=7"的来源与自我更正**：K=7 是 **本报告 §7.5 的一条提议**（"K=7 用 M6 现有数据"）——**该提议是错的**：M6 的 K=7 是 **旧配置（bf16/32K）+ 散文语料**，**不可作 A/B 基线**。⇒ **更正：N3 的 DFlash A/B 两边同跑 K=12（官方口径）**。不存在"强制降级到 K=7"。
